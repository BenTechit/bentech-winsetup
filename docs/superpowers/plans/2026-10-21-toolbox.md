# bentech-winsetup: the BenTech Toolbox (step 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A dark WPF window, the BenTech Toolbox, replaces the console start screen: Ben picks a built-in profile, adjusts Type, Office, Remote, 7-Zip, nine curated registry tweaks and a closing restore point, in English or Hebrew, and Start hands the Choices to the unchanged engine. A failure falls back to the console start screen.

**Architecture:**
- **Engine first (Task 1).** Three new Choices keys (`Profile`, `Tweaks`, `RestorePoint`), the `profiles` / `tweaks` / `toolbox` config sections, a `tweaks` step after `desktop-icons`, and a restore point at the very end of `Complete-SetupFinalization`. It all works with the console start screen alone: `New-DefaultChoices` returns the default profile.
- **One reader decides which tweaks run.** `Get-EffectiveTweaks` (in `Catalog.ps1`, like `Get-RemoteChoice`) applies the catalog and the `desktopOnly` / `office365Only` / `minBuild` rules. The plan, the step, the report, the window and the seam all go through it.
- **The window (Tasks 2-3)** is three files under `src\Toolbox\`: `Strings.ps1` (the only non-ASCII `src` file), `SetupPlanner.ps1` (pure: profiles, validation, the window model, the plan preview) and `Toolbox.ps1` (XAML here-string, view, handlers, lifecycle). The view renders a pure model; every handler is one line calling `Invoke-ToolboxAction`.
- **The seam (Task 4).** `Main.ps1:295` calls `Get-SetupChoices` with `Show-StartScreen`'s exact parameters and contract. Inside, the outcome is Start, Cancel or Failed; only Failed falls back to the console screen.

**Tech Stack:** Windows PowerShell 5.1, WPF (PresentationFramework, PresentationCore, WindowsBase from .NET Framework 4.8, loaded by `Add-Type`), the registry provider, `Checkpoint-Computer` / `Enable-ComputerRestore` / `Get-ComputerRestorePoint` (in a child process only), CIM `Win32_ComputerSystem`. Pester 6.2 on the dev PC only.

**Spec:** `docs/specs/2026-10-21-toolbox-design.md` (binding) and its fact cards `docs/specs/2026-10-21-toolbox-tweak-factcards.md` (exact registry values). They amend the v1, v2, Craft and ScreenConnect specs, which stay binding elsewhere. These travel with this plan and still apply:
- the Global Constraints of `docs/superpowers/plans/2026-10-20-progress-visibility.md`, `2026-10-20-craft-apps.md` and `2026-10-20-screenconnect.md`;
- the ledger rulings in `.superpowers/sdd/*/progress.md` (do not undo any; especially V2-R13 deletion safety, R26 Phase B always runs, the colour rule).

## Global Constraints

**Platform and safety**
- Windows PowerShell **5.1 only**. No modules, no downloads at run time, nothing installed. WPF comes from .NET Framework 4.8, which every target already has.
- **Never run `setup.ps1`, a setup step, the launcher, `Publish.ps1` (not even `-DryRun`), `msiexec` or any installer on this PC.** Tests mock the registry cmdlets, CIM, `Invoke-External`, `Invoke-PowerShellChild`, `Test-AdminProtection`, `Test-OnACPower`, `Save-RunState` where it matters. **No test writes the real registry** (not even HKCU).
- **No test opens a real window or stops WPF.** `ShowDialog()` is called only in the default value of `Show-ToolboxWindow -ShowDialog`; `Dispatcher.InvokeShutdown()` only in the default value of `Get-SetupChoices -ShutdownDispatcher`. Every test passes both seams (static guard in Task 4). Creating a `Window` with `XamlReader.Parse`, raising events on it and calling `Close()` on it is safe and is how the window is tested (proven on this PC on 21/10/2026: `Close()` on a never-shown window fires Closing and Closed; a second `Close()` is a no-op).
- **Outward-facing actions need Ben's explicit OK at that moment.** Never run `git push` or any `gh` command.
- **The launcher must not change.** `launcher\BenTechSetup.template.cmd` and `keys\public-key.xml` are not edited; `keys\launcher.sha256` stays `702c323aff5e813d7264375d15387d3bcdc12baded3d192f4bc47890663b69ff`. `src\Entry\Param.ps1` does not change (`tests\Bundle.Tests.ps1` pins it).

**Runtime rules (unchanged, and how they apply here)**
- **Child processes:** through `Invoke-External`. The restore point runs in one child through `Invoke-PowerShellChild` (Winget.ps1:323) with `timeoutsMinutes.restorePoint` (10).
- **No waiting without a deadline, no prompts, no `Start-Sleep`** in step or toolbox code (`tests\Waits.Tests.ps1` list unchanged). The window waits for Start on purpose (Q18); that is before anything runs.
- **`try` blocks:** `$ErrorActionPreference` stays `Continue`; registry cmdlets inside a `try` carry `-ErrorAction Stop`; a failing cmdlet is mocked with `Write-Error`, never `throw` (`tests\ErrorAction.Tests.ps1`).
- **Registry writes** only through `Set-RegistryDword` (Prepare.ps1:531) and its new REG_SZ twin `Set-RegistryString`. Types REG_DWORD and REG_SZ only; hives `HKCU:\`, `HKLM:\` and `Registry::HKEY_USERS\.DEFAULT\`; **no path containing `\Policies\`**; no value the run already manages.
- **Never parse localized output.** Administrator protection compares two account names; the restore point is confirmed by `SequenceNumber` and the child's exit code.

**Text, language and colour**
- Console, `setup.log`, `activity.txt` and the report are English and ASCII. **Nothing Hebrew reaches them**: Choices hold ASCII ids only; every exception message the toolbox logs goes through `ConvertTo-ScreenText`; notes use the tweak's English title.
- **`src\Toolbox\Strings.ps1` is the only `src` file with non-ASCII** (UTF-8 with BOM, as every `.ps1`). In `config\config.json` non-ASCII appears only inside `he` values.
- **Colours are hex values** in one `<Window.Resources>` dictionary. `DarkYellow` / `DarkMagenta` never appear in any `src` token, here-strings included (`tests\Colors.Tests.ps1`). The toolbox has no `Write-Host`.

**WPF rules (spec 5.1)**
- Every handler is one line: `{ Invoke-ToolboxAction -Sender $this }` (or with `-Action`). Window state lives in `$window.Tag`. No `GetNewClosure()`, no outer variables. The one exception: the dispatcher backstop reads `$script:ToolboxOpenWindow` (the dispatcher event has no window); **Plan call**.
- Every .NET call's output goes to `$null`; every function returns exactly one value or nothing (pinned by tests).
- `RenderOptions.ProcessRenderMode = SoftwareOnly`; Topmost at open, `Activate()` on ContentRendered, then Topmost off.
- **Start is never the default:** `IsDefault="False"`, `Focusable="False"` (so neither Enter nor Space can press it; **Plan call**). **Esc is unbound:** no `IsCancel`, no key bindings, no key handlers.
- A disabled button still runs its Click handler when the event is raised in code (proven on this PC). So the Start action itself refuses when Administrator protection is On.

**Values the spec pins** (full shapes in Shared shapes; copy them exactly)
- Catalog: `@{ Id = 'tweaks'; Title = 'System tweaks'; Short = 'Tweaks'; Function = 'Invoke-StepTweaks' }`, right after `desktop-icons`.
- Messages: `<Tweak title> could not be applied` (yellow Note), `<n> tweaks applied` (Done message, verbatim also for n = 1), `Per-user tweaks skipped: Windows Administrator protection is on` (Note), activity `Tweaks: <n> applied`, `Restore point could not be confirmed` (Note), red banner `Setup is running as a different user than the one signed in (Windows Administrator protection, or an admin password typed for another account). It would not resume after a restart: sign in as this PC's administrator, or turn Administrator protection off in Windows Security.` (**Ruling TB-R1**, the controller, 21/10/2026: a user mismatch also happens when an admin password is typed for a standard account, so the banner names both causes. Blocking stays.)
- Restore point: `HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SystemRestore` value `SystemRestorePointCreationFrequency`; `Checkpoint-Computer -Description 'BenTech setup' -RestorePointType MODIFY_SETTINGS`.
- Window: about 1000 x 680 DIPs; `#1E1E1E` background, `#252526` panels, `#F0F0F0` text, `#2D7DD2` accent, `#FFC83D` warnings; Segoe UI; glyphs `Segoe Fluent Icons, Segoe MDL2 Assets`; no image files.

**Files, tests, commits**
- Every `.ps1` is UTF-8 **with BOM**. After writing, re-save: `powershell -NoProfile -Command "Get-ChildItem -Recurse -Include *.ps1 src,tests,tools | % { $t=[IO.File]::ReadAllText($_.FullName); [IO.File]::WriteAllText($_.FullName,$t,(New-Object Text.UTF8Encoding $true)) }"` (ReadAllText reads BOM-less files as UTF-8, so Hebrew survives).
- **Test command:** `powershell -NoProfile -ExecutionPolicy Bypass -File tools\Invoke-Tests.ps1 -Path tests` (or one file). **Pass = the last line reads `Failed: 0`.** Today 2336 tests pass (about 6 minutes). Every task ends with the full suite green.
- A new `src` file needs its `$BundleOrder` entry **in the task that creates it** (`Build-Bundle.ps1` throws otherwise, and `Bundle.Tests` fails). **Plan call:** the brief put "Bundle order entries" in Task 4; Task 4 only verifies the final order.
- **Commits:** a review gate before every commit (Ben's rule). Conventional commits, each with a second `-m "Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>"`. Branch `feat/toolbox`.

## Review Focus

The five failure modes the spec implies that are most likely to bite, most likely first. Each names the test that pins it.

1. **An exception inside the window** (a handler, the view, WPF itself) leaving a frozen or hidden window, or being read as Cancel (which would end the run and delete the folder).
   - Expected: the window closes as **Failed**, the console start screen opens, and setup.log gets one ASCII ERROR line even when the message held Hebrew.
   - Tests: Task 3 `'an exception inside an action closes the window as Failed, never as Cancel (Review Focus 1)'` and the backstop test; Task 4 `'Failed falls back to the console; a throwing toolbox is Failed, never Cancel (Review Focus 1)'`.
2. **Choices that are not one hashtable**, because a .NET call leaked output (`Children.Add` returns an int) into a function's result.
   - Expected: `New-ToolboxWindow` returns one `Window`; `Show-ToolboxWindow` one result hashtable; `Get-SetupChoices` one Choices hashtable or one `$null`.
   - Tests: Task 2 `'New-ToolboxWindow returns exactly one Window and the view returns nothing (Review Focus 2)'`; Task 3 `'returns exactly one hashtable with the Choices on Start (Review Focus 2)'`; Task 4 `'Start returns the validated Choices, once, and stops WPF once (Review Focus 2)'` and the Cancel test (one `$null`).
3. **The console fallback silently dropping or adding tweaks.**
   - Expected: the console path runs the default profile's tweaks; L drops NumLock, D brings it back, O to 365 adds classic Outlook; the Choices that leave `Get-SetupChoices` by either path hold the same effective tweak list.
   - Tests: Task 1 `'the console fallback keeps the profile''s tweaks and follows L, D and O (Review Focus 3)'`; Task 4 `'the console and the window return the same tweaks for the same options (Review Focus 3)'`.
4. **A registry write Windows refuses, a wrong value type, or HKCU on an Administrator-protection PC.**
   - Expected: UCPD's "Access is denied" is a yellow Note for that tweak only, never a red step; the accessibility `Flags` stay REG_SZ; with protection On every HKCU value is skipped (one Note), the `HKU\.DEFAULT` NumLock value still applies, and the window's Start is disabled and refuses a raised click.
   - Tests: Task 1 `'a write Windows refuses is a yellow Note, never red (Review Focus 4)'`, `'clearBit keeps the Flags REG_SZ ...'`, `'Administrator protection On: no HKCU write ...'`; Task 3 `'Administrator protection On: red banner, Start disabled, a raised click refused (Review Focus 4)'`.
5. **The restore-point frequency value left at 0** after a child that times out, fails to start or exits non-zero, or after a second finalize pass.
   - Expected: the main process puts the original back (or deletes the value when it was absent) in every path; a repeated finalize never tries again.
   - Test: Task 1 `'the frequency value is put back whatever the child does (Review Focus 5)'`.

### Choices (Task 1)

```
@{ Mode = 'LAPTOP'|'DESKTOP'; SevenZip = <bool>; Office = 'CRAFT'|'BUSINESS'|'HOME'|'OFF'
   Remote = 'ANYDESK'|'SCREENCONNECT'|'BOTH'
   Profile = '<profile id>' | ''          # '' = no profile
   Tweaks = [string[]]                    # tweak ids, ASCII, catalog order
   RestorePoint = <bool> }
```
- **What `Tweaks` holds.**
  - `New-DefaultChoices` and the window model hold the profile's **selection**: catalog ids, not yet filtered by the Type/Office/build rules. So the console's L / D / O can bring NumLock and classic Outlook back.
  - `ConvertTo-ValidChoices` (at the seam and on Start) turns it into the **effective list**, so state.json records what will run.
  - Every reader (plan, step, report) still calls `Get-EffectiveTweaks`, which is idempotent.

### The tweak catalog and its rules (Task 1)

`Get-TweakCatalog -Config` emits one hashtable per **valid** entry, in config order:
```
@{ Id; Default = <bool>; DesktopOnly = <bool>; Office365Only = <bool>; MinBuild = <int, 0 = none>; Icon = '<hex>'
   Title = @{ en; he }; Description = @{ en; he }
   Values = @( @{ Path; Name; Type = 'String'|'DWord'; Op = 'set'|'clearBit'; Bit = <long>|$null; Value } ) }
```
An entry is left out (silently; `tests\Config.Tests.ps1` proves all nine survive) when any of these fails:
- the id matches `^[A-Za-z][A-Za-z0-9]{0,31}$` and is not a duplicate (the first one wins);
- `title.en` is not empty, and `values` is not empty;
- for each value:
  - the path starts with `HKCU:\`, `HKLM:\` or `Registry::HKEY_USERS\.DEFAULT\` (case-insensitive) and contains no `\Policies\`;
  - the type is `String` or `DWord`, the op `set` or `clearBit`;
  - `clearBit` needs `String`, a power-of-two `bit` in 1..0x80000000 and a decimal-digit `value`;
  - a DWord `set` needs an integer `value` in 0..0x7FFFFFFF;
  - a String value is a string (may be empty);
  - the name is a string, empty only for a String `set`.

`Test-TweakAllowed -Tweak -Choices -Machine` is `$false` when any rule fails:
- `DesktopOnly`, and `Choices.Mode` is not `DESKTOP`;
- `Office365Only`, and `Choices.Office` (upper-cased) is not `BUSINESS` or `HOME`;
- `MinBuild -gt 0`, and `Machine.OsBuild` is known (`-gt 0`) and below it.

**Plan call:** an unknown build does not filter; production always knows it.

`Get-EffectiveTweaks -Choices -Config [-Machine]`:
- the catalog entries whose id is in `@($Choices['Tweaks'])` (case-sensitive, after a `[string]` cast) and that pass `Test-TweakAllowed`;
- in catalog order, each once;
- missing or `$null` Choices or Tweaks give nothing;
- pure, no logging.

### Restore point (Task 1)

`$script:RestorePointCommand` (Finalize.ps1, exact text; Invoke-PowerShellChild prepends `$ProgressPreference = 'SilentlyContinue';`):
```powershell
$script:RestorePointCommand = @'
$ErrorActionPreference = 'Stop'; $d = $env:SystemDrive + '\'
Enable-ComputerRestore -Drive $d
$b = [long](@(@(Get-ComputerRestorePoint | ForEach-Object { [long]$_.SequenceNumber }) + 0) | Measure-Object -Maximum).Maximum
Checkpoint-Computer -Description 'BenTech setup' -RestorePointType MODIFY_SETTINGS
$a = [long](@(@(Get-ComputerRestorePoint | ForEach-Object { [long]$_.SequenceNumber }) + 0) | Measure-Object -Maximum).Maximum
if ($a -gt $b) { exit 0 } else { exit 3 }
'@
```
Exit 0 = a new point confirmed; 1 = an error stopped it; 3 = no new point.

| Case | Returns | State | Note |
|---|---|---|---|
| `Choices.RestorePoint -ne $true` | `NotChosen` | untouched | |
| `State.RestorePointTried -eq $true` already | `Created` if `State.RestorePointCreated -eq $true`, else `NotConfirmed` | untouched; **no child** | `Restore point could not be confirmed` when NotConfirmed |
| Saving `RestorePointTried = $true` throws | `NotConfirmed` | `RestorePointTried` stays `$true` in memory | the Note; **no child, frequency untouched** (**Plan call**) |
| Child exit 0, not timed out | `Created` | `RestorePointCreated = $true` | |
| Timeout, exit non-zero, `$null` exit, child cannot start | `NotConfirmed` | `RestorePointCreated = $false` | the Note |
| The frequency value is not back afterwards (any case that touched it) | as above | | also `Restore point frequency value could not be put back` (**Plan call**: a new Note, so a value stuck at 0 is never silent) |

- **Order in `Invoke-SetupRestorePoint`:**
  1. Record the original with `Get-RegistryValue` (logged: its value, or `absent`).
  2. `Set-RegistryDword ... -Value 0`. A refusal is logged WARN; the child still runs, and its sequence check decides.
  3. `Set-SetupNow -SubTitle 'Creating a restore point'`.
  4. The child, inside `try`.
  5. `finally`, whatever the child did:
     - an original that existed is written back with `Set-RegistryDword`; an absent one is removed with `Remove-RegistryValueIfPresent`;
     - then it is read back to check;
     - `Set-SetupNow -SubTitle ''`.
- **On Created:** activity `Restore point created` (**Plan call**).
- **Timeout:** `[double]Config.timeoutsMinutes.restorePoint`, or 10 when missing or not above 0.
