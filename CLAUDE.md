# CLAUDE.md: bentech-winsetup

Zero-touch Windows post-install setup tool for Ben's repair shop (BENTECH IT). A signed `.cmd` launcher downloads and verifies `setup.ps1` + `config.json` from this repo's latest GitHub Release and runs them as admin on customer PCs. **It runs as admin on other people's machines: every change is judged by that.**

This is a PowerShell project. Ben's global rules for Node/TypeScript, the API envelope, Hebrew-first UI and RTL do **not** apply here: the console UI is English and ASCII only (spec section 5). His review, planning and outward-facing rules do apply (below).

## Stack
- Windows PowerShell **5.1 only**. No modules, no dependencies on target machines. Pester 5.5+ on the dev PC only.
- Targets: Windows 11 25H2/26H2 Home/Pro (main), Windows 10 22H2 (best effort), x64 (ARM64 best effort).
- Launcher: ASCII-only polyglot `.cmd` (CRLF). Data lives in `config/config.json`.

## Hard rules (Global Constraints, condensed)
- **Never parse localized output** (Hebrew Windows). Use exit codes, CIM, registry values, GUIDs, SIDs. The one exception: hex values in `powercfg /query`.
- Every `.ps1` is **UTF-8 with BOM** (the file-writing tool emits none: re-save; `tests/Encoding.Tests.ps1` enforces it). `.gitattributes` marks `*.ps1`, `*.json`, `*.cmd`, `*.xml` as `-text`: Git must never rewrite line endings.
- Downloads: `System.Net.WebClient` + TLS 1.2. **Never `Invoke-WebRequest`** (it prompts without `-UseBasicParsing`).
- Every child process goes through `Invoke-External` with a timeout from `config.timeoutsMinutes`. **The one exception is the Office background process** (`Start-BackgroundExternal`, started by the `office` step): its deadline (`timeoutsMinutes.office` after its start) is enforced by `Wait-OfficeBackground`, which `office-finish`, every controlled restart and Finalize call. Nothing may wait without a deadline.
- Steps never prompt: no `Read-Host`, no `-Confirm`, no `pause`. Nothing may stop and wait.
- `$ErrorActionPreference` stays `Continue`, so a cmdlet failure inside a `try` is only caught with `-ErrorAction Stop`: CDXML/CIM (`Register-ScheduledTask`) and registry/file provider cmdlets fail non-terminating. `tests/ErrorAction.Tests.ps1` enforces it for `New-Item`, `New-ItemProperty`, `Set-ItemProperty`, `Remove-ItemProperty` and the `*-ScheduledTask` cmdlets; mock a failing cmdlet with `Write-Error`, never `throw`.
- Console text is English; report dates are `dd/MM/yyyy HH:mm`. No secrets anywhere, no customer PII beyond machine identity, except that ScreenConnect, when chosen, is the one unattended remote tool and enrols the PC in Ben's ScreenConnect cloud (screenconnect spec 4.6).
- Signature scheme: RSA-3072, PKCS#1 v1.5, SHA-256, detached `<file>.sig` over the **raw bytes**. Verify fails closed.
- Working folder `C:\BenTech\Setup`; resume task `BenTechSetup-Resume`. `C:\BenTech` is admin-only, created by the launcher, **never repaired and never ACL'd recursively** (R28b/R28c): an existing one is verified or the launcher refuses (exit 5).

## Screens, ticks and activity (v2)
- **Colours** (`tests\Colors.Tests.ps1`): no screen uses `DarkYellow` or `DarkMagenta` (the `powershell.exe` console profile remaps them to near white and PowerShell blue). **Every screen line sets its foreground and its background explicitly**: each `Write-Host` under `src` passes both `-ForegroundColor` and `-BackgroundColor`, and every `[Console]` frame write passes both. Verdict colours: YELLOW = Black on Yellow, GREEN = White on DarkGreen, RED (and anything unknown) = White on DarkRed; the start and progress screens draw on Black.
- **Drawing:** the start, progress and final screens draw through the console writer (`New-ConsoleWriter`, `src\UI\ConsoleFrame.ps1`), never `Write-Host` or `Clear-Host`: `Start-Transcript` records every `Write-Host`, so a redraw every second would flood the transcript. Only the reboot countdown, the cleanup messages, the crash text and the "already running" line still use `Write-Host`.
- **The tick:** `Register-SetupTick` / `Invoke-SetupTick` redraw the progress screen at most once a second, from `Invoke-External`'s poll loop, from `Wait-SetupDelay` and from the download loop. **Step code never calls `Start-Sleep`: it calls `Wait-SetupDelay`** (with no tick registered that is exactly one `Start-Sleep` with the same argument; `tests\Waits.Tests.ps1` lists the only places allowed to sleep). **The tick never throws** (its errors are logged at most once a minute), costs about 50 ms, reads at most the last 64 KB of any file, and **never runs in the `-WuRound` child** or before `Register-SetupTick`.
- **Activity:** facts for the JUST HAPPENED feed go through `Add-SetupActivity -Text` (never throws; appends to `Logs\activity.txt` and writes `setup.log`; the runner writes the step lines itself). **The AnyDesk ID never goes into `setup.log`**: pass `-LogText` without it (the screen, `activity.txt` and the report may hold it). The live NOW detail comes from `Set-SetupNow -SubTitle / -Provider`, which the runner clears around every step. Console text is ASCII (`ConvertTo-ScreenText` on every free-text value); vendor logs and Windows Update titles are read for display only, with a silent fallback, and no decision depends on them.
- **Config switches:** `windowsUpdate.installMode` is `OneAtATime` (the default) or `Batch` (v1's one-go install). The optional `vendors.<BRAND>.consumerApp.verify` (`paths` and/or `services`) makes the vendor-app step check the app after winget reports success; without it the step is Done on winget's word (v1). Its shape is pinned in `tests\Config.Tests.ps1`.

## Cleanup: no leftover folder (v2 spec 10)
- **`C:\BenTech` is deleted only by `Remove-SetupFolder`**: `cmd.exe /d /c rd /s /q` through `Invoke-External` (`rd` removes a junction without following it; `Remove-Item -Recurse` on 5.1 would follow it). `Remove-SetupFolder` itself only refuses a path that is not fully qualified, whose leaf is not `BenTech`, a drive root or a reparse point. The rule "only `%SystemDrive%\BenTech`" is enforced one level up, in `Invoke-SetupCleanup`, which hands `Remove-SetupFolder` no other path (anything else: `Not deleting ...`). `Copy-SetupLogsToStick` follows the same rule: it refuses a `BenTech-Logs` that is a link and replaces the old folder with `rd`. Never `Remove-Item -Recurse` on anything that could hold a link.
- It runs **only after Enter on the final screen** (`Invoke-SetupCleanup -Mode Finish`: the logs to `<stick>\BenTech-Logs\<PC name>`, a Desktop launcher deleted only when it is a `.cmd` file, then the folder) **or after Esc on the start screen when no earlier run state existed** (`-Mode Cancel`). **Never after a crash, a restart or a lock held by another run.** It runs after the transcript is stopped and the lock released.
- The stick is the drive with the launcher's volume serial (not when the launcher ran from a Desktop), else a removable or fixed drive other than the system drive with `BenTechSetup.cmd` in its root.
- **Tests never delete anything outside `$TestDrive`.** `tests\Entry.Tests.ps1` mocks `Invoke-SetupCleanup` in its `BeforeEach` (its `-Root` is `$TestDrive`, whose parent is the temp folder); the one real `rd` test works inside `$TestDrive` on a folder named `BenTech`.

## Step contract and shapes
- Every step is `Invoke-Step<Name> -Context <hashtable>` and returns `New-StepResult` (`Status` Done/Skipped/Failed/Continue, `Message`, `Reboot` None/Now, `Notes` = yellow, `Errors` = red, `Data`). Always set a `Message` on Skipped/Failed. `Continue` means "call me again".
- **Step order** (`src/Engine/Catalog.ps1`): prepare, bitlocker, region, desktop-icons, bloatware, rename, winget, chrome, anydesk, **screenconnect**, 7zip, **craft-apps**, default-browser, vendor-pass1, **office**, windows-update, **office-finish**, vendor-pass2, consumer-app, vendor-cleanup, finalize. `office` comes right after `vendor-pass1` and starts the ODT `setup.exe` in the background (every Windows Installer install and every restart a vendor tool forces thus happens before it); `office-finish` comes right after `windows-update`, collects the result, makes at most one foreground retry and adds the shortcuts. Both are in the plan only with Office BUSINESS or HOME (CRAFT and OFF leave both out); the progress screen folds `office-finish` into the Microsoft 365 line.
- `Choices.Office` is `CRAFT` (the default) | `BUSINESS` | `HOME` | `OFF`; **O** cycles them in that order. CRAFT plans `craft-apps` (after `7zip`) instead of `office` and `office-finish`; BUSINESS and HOME plan what they did before.
- `Choices.Remote` is `ANYDESK` (the default) | `SCREENCONNECT` | `BOTH`; **R** cycles them in that order. Every reader goes through `Get-RemoteChoice` (a missing or invalid value means ANYDESK), never through the plan list. `anydesk` runs with ANYDESK or BOTH, `screenconnect` with SCREENCONNECT or BOTH.
- `craft-apps` (`src/Steps/CraftApps.ps1`): each `apps.craft.items` MSI from GitHub `releases/latest` runs only after its `SHA256SUMS.txt` line and an **exact** signer CN (`Test-FileSignature -ExactCN`; a company name, never a thumbprint: the certificates live 3 days). It deletes only an MSI that failed a check (V2-R13). Shortcuts are never overwritten, deleted, guessed or moved between desktops (C-R3, C-R4). A failed app is red; the launcher or a shortcut alone is yellow. `displayName`/`startMenuName` are guesses until `docs/testing.md` 1.17; details in README "Changing apps and lists".
- `screenconnect` (`src/Steps/ScreenConnect.ps1`): Ben's installer, fetched from **this release's own** URL (`v{version}`, never `latest`), runs only after its SHA-256 equals the pin in the signed `config.json` (the real proof it is Ben's file) **and** `Test-FileSignature` passes on the quoted signer `"ConnectWise, LLC"` (a substring match: **never `-ExactCN`**, it refuses a quoted subject). It deletes only an installer that failed a check (V2-R13). The exit code decides nothing: the service (read by its exact name) does. It is the one unattended remote tool and enrols the PC in Ben's list on purpose (screenconnect spec 4.6); publishing and renewal: README "A new ScreenConnect installer".
- Steps are listed in `src/Engine/Catalog.ps1`; a new step needs a catalog entry, its `Invoke-Step*` function, a `$BundleOrder` entry in `tools/Build-Bundle.ps1` (when it is a new file) and tests.
- **State** (`state.json`) shape: `New-RunState` in `src/State/State.ps1` and "Shared shapes" in the plan. Keep step `Data` shallow (`ConvertTo-Json -Depth 12` truncates silently); the key `Interruptions` is reserved by the runner.
- Context: `@{ Config; State; Root; LogDir; DownloadDir; ScriptPath; StatePath }`.
- `Get-StepPlan` returns plain ids (no comma-wrapping). `$PSScriptRoot` is empty in `param()` defaults of a `[CmdletBinding()]` script on 5.1: resolve it in the body.

## Sign and publish flow (R29)
- Private key: `%USERPROFILE%\.bentech-winsetup\signing-key.dpapi` (DPAPI, never in the repo). Public key: `keys/public-key.xml`, built into every launcher. **The private-key backup MUST be in Ben's password manager before the first publish; verify it** (README "Signing key" has the procedure). The private key must never be written to a file outside the DPAPI store (except a short-lived `-BackupPath` file such as `bentech-signing-key-BACKUP.xml`, in a non-synced folder, deleted permanently as soon as the password manager holds the key), and never put in a synced folder, a repo, or a chat. Moving it into the password manager through the clipboard is the intended route (README procedure, with Windows clipboard history and sync OFF).
- `tools/Publish.ps1 -Version yyyy.MM.dd.N [-Notes ..] [-DryRun]`: needs a clean tree and a pushed HEAD (warnings only under `-DryRun`), runs the tests, builds the bundle, signs, verifies, builds the launcher, then `gh release create v<Version> --target <HEAD>` with exactly **five** files: the four signed ones (`setup.ps1`, `config.json` and their `.sig`) plus `ScreenConnect.ClientSetup.exe` (no `.sig`: `config.json` pins its SHA-256). Publish reads that installer from `%USERPROFILE%\.bentech-winsetup\` and checks it before building (it exists, its SHA-256 matches, a `Valid` ConnectWise signature; `-DryRun` only warns). The launcher still fetches only the four signed files.
- **R29: the launcher is never uploaded.** It is the trust anchor (it holds the public key). Publish prints its SHA-256 and records it in `keys/launcher.sha256`; Ben keeps `dist\BenTechSetup.cmd` on his USB stick and re-copies it only when that hash changes (new key or changed template). Commit the updated hash file.
- The v2, Craft and ScreenConnect work left the launcher untouched: `launcher\BenTechSetup.template.cmd` and `keys\public-key.xml` are unchanged and `keys\launcher.sha256` stays `702c323a...` (pinned by `tests\Launcher.Tests.ps1`). A publish dry run must not print `WARNING: the launcher changed`; if it does, every USB stick needs the new launcher.
- R30: the launcher calls `powershell.exe` and `fltmc.exe` by full path. Its own path reaches PowerShell only through `set "BT_SELF=%~f0"` / `$env:BT_SELF`, never inside a quoted PowerShell string (an apostrophe in the path would break it).
- Launcher exit codes: 0 ok, 1 unexpected error, 2 already running, 3 signature check failed, 4 cannot download, 5 cannot secure `C:\BenTech`.
- Rollback: `gh release edit v<old> --latest`. A lost key means a new key and a new launcher on every stick.

## Never on the dev PC
- **Never run setup steps, `setup.ps1`, the launcher, `msiexec` or a downloaded installer on this machine.** In particular never run `ScreenConnect.ClientSetup.exe` (any copy, in `Downloads\` or `%USERPROFILE%\.bentech-winsetup\`): it would enrol this PC in Ben's ScreenConnect list; and no test may read Ben's real installer. They reboot, uninstall apps, change power plans, ACLs, BitLocker and policies. Tests mock everything (registry, CIM, Task Scheduler, icacls, WUA COM, `Invoke-External`, `Start-BackgroundExternal`, `Get-RemoteText`/`Get-RemoteFile`, `Test-FileSignature`, the desktop folders, `WScript.Shell`, the `[Console]` writer).
- **Outward-facing actions need Ben's explicit OK at that moment:** creating the public repo, `git push`, publishing a Release. Never run `gh repo`, `gh release`, `git push` or `Publish.ps1` without `-DryRun` on your own.

## Tests and commits
- `powershell -NoProfile -ExecutionPolicy Bypass -File tools\Invoke-Tests.ps1 -Path tests` (or one file). **Pass = the last line reads `Failed: 0`.**
- Conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`). Review gate before every commit; run the `code-review` command before a PR (Ben's rules).
- Things only a real machine can prove are listed in `docs/testing.md`. Add to it whenever something is verified by mocks only.
