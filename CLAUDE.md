# CLAUDE.md: bentech-winsetup

Zero-touch Windows post-install setup tool for Ben's repair shop (BENTECH IT). A signed `.cmd` launcher downloads and verifies `setup.ps1` + `config.json` from this repo's latest GitHub Release and runs them as admin on customer PCs. **It runs as admin on other people's machines: every change is judged by that.**

This is a PowerShell project. Ben's global rules for Node/TypeScript, the API envelope, Hebrew-first UI and RTL do **not** apply here: the console UI is English and ASCII only (spec section 5), **and the one exception is the toolbox window** (see "The toolbox window" below; the Repair & diagnostics reports on the stick are UTF-8 too, see "Repair & diagnostics"). His review, planning and outward-facing rules do apply (below).

## Stack
- Windows PowerShell **5.1 only**. No modules, no dependencies on target machines. Pester 5.5+ on the dev PC only.
- Targets: Windows 11 25H2/26H2 Home/Pro (main), Windows 10 22H2 (best effort), x64 (ARM64 best effort).
- Launcher: ASCII-only polyglot `.cmd` (CRLF). Data lives in `config/config.json`.

## Hard rules (Global Constraints, condensed)
- **Never parse localized output** (Hebrew Windows). Use exit codes, CIM, registry values, GUIDs, SIDs. The one exception: hex values in `powercfg /query`.
- Every `.ps1` is **UTF-8 with BOM** (the file-writing tool emits none: re-save; `tests/Encoding.Tests.ps1` enforces it). `.gitattributes` marks `*.ps1`, `*.json`, `*.cmd`, `*.xml` as `-text`: Git must never rewrite line endings.
- Downloads: `System.Net.WebClient` + TLS 1.2. **Never `Invoke-WebRequest`** (it prompts without `-UseBasicParsing`).
- Every child process goes through `Invoke-External` with a timeout from `config.timeoutsMinutes`. **There are three named exceptions**, the first two started through `Start-BackgroundExternal` (repair spec 10):
  - **the Office background process** (started by the `office` step): its deadline (`timeoutsMinutes.office` after its start) is enforced by `Wait-OfficeBackground`, which `office-finish`, every controlled restart and Finalize call;
  - **the toolbox's action child** (`setup.ps1 -ToolAction <id> -ToolArgs <args.json>`, started by the window without waiting): its deadline is enforced by the window's run timer, on a per-run Stopwatch (budget `timeoutsMinutes.tool.<id>`, the kill at budget + 3 minutes: RD-R8, RD-R9). "Open folder" starts `explorer.exe` the same way and never waits for it;
  - **the final screen's B, R and U keys** open Default apps, Notepad and Settings with `Start-Process` (its `-Launch` seam): they start them and never wait for them, so there is no deadline to keep.

  Nothing may wait without a deadline. Inside the action child every native tool goes through `Invoke-External` (`Invoke-ToolNative`, `timeoutsMinutes.toolStep`), and **every cmdlet that can hang** (`Get-PhysicalDisk`, `Get-StorageReliabilityCounter`, `Repair-WindowsImage`, `Repair-Volume`, `Get-WindowsDriver`, `Get-Printer`, the PnpDevice, NetTCPIP, BitsTransfer and Defender cmdlets) runs only in a bounded grandchild (`Invoke-ToolJsonChild`), never in the child's own process and never on the window's thread. **Event-log queries** run in grandchildren too (the reports' events command, `$script:ReportEventsCommand`), with **one exception**: the safety child's disk chip reads the System log's disk events in its own process (`Get-ToolDiskEventCount` in `ToolSafety.ps1`, `Get-WinEvent` with a start date and IDs). It is bounded only by the safety action's budget (3 minutes) and the window's kill at budget + 3 minutes; moving it into a grandchild is a final-wave item. Never on the window's thread either way.
- Steps never prompt: no `Read-Host`, no `-Confirm`, no `pause`. Nothing may stop and wait.
- `$ErrorActionPreference` stays `Continue`, so a cmdlet failure inside a `try` is only caught with `-ErrorAction Stop`: CDXML/CIM (`Register-ScheduledTask`) and registry/file provider cmdlets fail non-terminating. `tests/ErrorAction.Tests.ps1` enforces it for `New-Item`, `New-ItemProperty`, `Set-ItemProperty`, `Remove-ItemProperty` and the `*-ScheduledTask` cmdlets; mock a failing cmdlet with `Write-Error`, never `throw`.
- **The one non-ASCII exception is the toolbox window** (toolbox spec 4.3): `src\Toolbox\Strings.ps1` is the only non-ASCII `src` file (UTF-8 with BOM; `tests/Encoding.Tests.ps1` enforces both). **Hebrew never reaches `setup.log`, the console, `activity.txt` or the report**: Choices hold ASCII ids only, every exception message the toolbox logs goes through `ConvertTo-ScreenText`, and notes use the tweak's English title. In `config.json` non-ASCII appears only inside `he` values. For the same reason `Prepare.ps1`'s registry helpers (`Set-RegistryDword`, `Set-RegistryString`, `Get-RegistryValue`) call `ConvertTo-ScreenText` (from `StartScreen.ps1`) on the exception text they log; the bundle holds every file. The Hebrew YES (`טקד`) lives as code points (`0x05D8, 0x05E7, 0x05D3`) in `RepairPlanner.ps1`.
- **Repair & diagnostics text** (repair spec 6.8, 10): **the diagnostic reports on the stick are UTF-8 and may hold Hebrew data** (event messages, program names, the customer complaint): the core, the SAFE copy and the comparison with a BOM, and the files Ben reads, a report's `_data.json` and the network backup, as plain UTF-8 (`Write-ToolJsonFile -Utf8`, ruling RD-R23). Their headings, fact names and flags stay English ASCII. **`setup.log`, the child's log and the exchange files stay ASCII**: `args.json`, `progress.json` and `result.json` are ASCII bytes, a display-only name (a ghost device's, an adapter's) as `\uXXXX` escapes (`ConvertTo-ToolAsciiJson`, ruling RD-R21), and every log line takes `ConvertTo-ScreenText`.
- **PowerShell 5.1: never `@(...)` around a `List[object]`**: it throws "Argument types do not match". Use `.ToArray()` or a `foreach`.
- **The window uses hex colours** in one resource dictionary (`DarkYellow` and `DarkMagenta` never appear in any `src` token, here-strings included: `tests/Colors.Tests.ps1`). **No test opens a window or stops WPF**: `ShowDialog()` appears in `src` only as the default of `Show-ToolboxWindow -ShowDialog`, and `Dispatcher.InvokeShutdown()` only as the default of `Get-SetupChoices -ShutdownDispatcher` (static tests pin both). Creating a `Window` with `XamlReader.Parse`, raising events on it and `Close()` is safe, and is how the window is tested.
- Console text is English; report dates are `dd/MM/yyyy HH:mm`. No secrets anywhere, no customer PII beyond machine identity, except that ScreenConnect, when chosen, is the one unattended remote tool and enrols the PC in Ben's ScreenConnect cloud (screenconnect spec 4.6).
- Signature scheme: RSA-3072, PKCS#1 v1.5, SHA-256, detached `<file>.sig` over the **raw bytes**. Verify fails closed.
- Working folder `C:\BenTech\Setup`; resume task `BenTechSetup-Resume`. `C:\BenTech` is admin-only, created by the launcher, **never repaired and never ACL'd recursively** (R28b/R28c): an existing one is verified or the launcher refuses (exit 5).

## Screens, ticks and activity (v2)
- **Colours** (`tests\Colors.Tests.ps1`): no screen uses `DarkYellow` or `DarkMagenta` (the `powershell.exe` console profile remaps them to near white and PowerShell blue). **Every screen line sets its foreground and its background explicitly**: each `Write-Host` under `src` passes both `-ForegroundColor` and `-BackgroundColor`, and every `[Console]` frame write passes both. Verdict colours: YELLOW = Black on Yellow, GREEN = White on DarkGreen, RED (and anything unknown) = White on DarkRed; the start and progress screens draw on Black.
- **Drawing:** the console start screen (now the toolbox's fallback), the progress and the final screens draw through the console writer (`New-ConsoleWriter`, `src\UI\ConsoleFrame.ps1`), never `Write-Host` or `Clear-Host`: `Start-Transcript` records every `Write-Host`, so a redraw every second would flood the transcript. Only the reboot countdown, the cleanup messages, the crash text and the "already running" line still use `Write-Host`.
- **The tick:** `Register-SetupTick` / `Invoke-SetupTick` redraw the progress screen at most once a second, from `Invoke-External`'s poll loop, from `Wait-SetupDelay` and from the download loop. **Step code never calls `Start-Sleep`: it calls `Wait-SetupDelay`** (with no tick registered that is exactly one `Start-Sleep` with the same argument; `tests\Waits.Tests.ps1` lists the only places allowed to sleep). **The tick never throws** (its errors are logged at most once a minute), costs about 50 ms, reads at most the last 64 KB of any file, and **never runs in the `-WuRound` child** or before `Register-SetupTick`.
- **Activity:** facts for the JUST HAPPENED feed go through `Add-SetupActivity -Text` (never throws; appends to `Logs\activity.txt` and writes `setup.log`; the runner writes the step lines itself). **The AnyDesk ID never goes into `setup.log`**: pass `-LogText` without it (the screen, `activity.txt` and the report may hold it). The live NOW detail comes from `Set-SetupNow -SubTitle / -Provider`, which the runner clears around every step. Console text is ASCII (`ConvertTo-ScreenText` on every free-text value); vendor logs and Windows Update titles are read for display only, with a silent fallback, and no decision depends on them.
- **Config switches:** `windowsUpdate.installMode` is `OneAtATime` (the default) or `Batch` (v1's one-go install). The optional `vendors.<BRAND>.consumerApp.verify` (`paths` and/or `services`) makes the vendor-app step check the app after winget reports success; without it the step is Done on winget's word (v1). Its shape is pinned in `tests\Config.Tests.ps1`.

## Cleanup: no leftover folder (v2 spec 10)
- **`C:\BenTech` is deleted only by `Remove-SetupFolder`**: `cmd.exe /d /c rd /s /q` through `Invoke-External` (`rd` removes a junction without following it; `Remove-Item -Recurse` on 5.1 would follow it). `Remove-SetupFolder` itself only refuses a path that is not fully qualified, whose leaf is not `BenTech`, a drive root or a reparse point. The rule "only `%SystemDrive%\BenTech`" is enforced one level up, in `Invoke-SetupCleanup`, which hands `Remove-SetupFolder` no other path (anything else: `Not deleting ...`). `Copy-SetupLogsToStick` follows the same rule: it refuses a `BenTech-Logs` that is a link and replaces the old folder with `rd`. Never `Remove-Item -Recurse` on anything that could hold a link.
- It runs **only after Enter on the final screen** (`Invoke-SetupCleanup -Mode Finish`: the logs to `<stick>\BenTech-Logs\<PC name>`, a Desktop launcher deleted only when it is a `.cmd` file, then the folder) **or after Cancel on the start screen (the toolbox's Cancel, X or Alt+F4, or Esc on the console one) when no earlier run state existed** (`-Mode Cancel`). **Never after a crash, a restart or a lock held by another run.** It runs after the transcript is stopped and the lock released. **Never under a live toolbox child** (ruling RD-R17): when a child the window started survives every kill, `Start-BenTechSetup` skips the cleanup (Cancel and Finish) with a WARN and keeps `C:\BenTech` (the child's own deadline ends it); a requested Restart PC still goes ahead.
- The stick is the drive with the launcher's volume serial (not when the launcher ran from a Desktop), else a removable or fixed drive other than the system drive with `BenTechSetup.cmd` in its root.
- **Tests never delete anything outside `$TestDrive`.** `tests\Entry.Tests.ps1` mocks `Invoke-SetupCleanup` in its `BeforeEach` (its `-Root` is `$TestDrive`, whose parent is the temp folder); the one real `rd` test works inside `$TestDrive` on a folder named `BenTech`.

## Step contract and shapes
- Every step is `Invoke-Step<Name> -Context <hashtable>` and returns `New-StepResult` (`Status` Done/Skipped/Failed/Continue, `Message`, `Reboot` None/Now, `Notes` = yellow, `Errors` = red, `Data`). Always set a `Message` on Skipped/Failed. `Continue` means "call me again".
- **Step order** (`src/Engine/Catalog.ps1`): prepare, bitlocker, region, desktop-icons, **tweaks**, bloatware, rename, winget, chrome, anydesk, **screenconnect**, 7zip, **craft-apps**, default-browser, vendor-pass1, **office**, windows-update, **office-finish**, vendor-pass2, consumer-app, vendor-cleanup, finalize. `office` comes right after `vendor-pass1` and starts the ODT `setup.exe` in the background (every Windows Installer install and every restart a vendor tool forces thus happens before it); `office-finish` comes right after `windows-update`, collects the result, makes at most one foreground retry and adds the shortcuts. Both are in the plan only with Office BUSINESS or HOME (CRAFT and OFF leave both out); the progress screen folds `office-finish` into the Microsoft 365 line. `windows-update` with `Choices.WindowsUpdate` DRIVERS searches `Type='Driver'` only (the child reads the choice from `state.json` and gets `Invoke-WuRound -Scope`; no new switch, so `Param.ps1` and the launcher do not change). Optional drivers stay skipped; DRIVERS round 1 counts them in `setup.log` (`Optional driver updates skipped`, ruling WU-R1), last in the round, after its installs (ruling WU-R3), and not at all when the round threw. **The round's result is written before the count** (ruling WU-R5), and a parent whose round timed out uses a result the round already wrote (WARN `Windows Update round timed out after its result was written`; with none, or one that cannot be read, it is still `Windows Update round timed out`), so a hanging count can still cost time up to the round's deadline, never the drivers or the round's result (`docs/testing.md` 1.20 measures the count).
- `tweaks` (`src/Steps/Tweaks.ps1`) is planned only when `Get-EffectiveTweaks` names at least one tweak; it lands before the first restart, so Explorer picks the values up at the next sign-in.
- `Choices.Office` is `CRAFT` (the default) | `BUSINESS` | `HOME` | `OFF`; **O** cycles them in that order. CRAFT plans `craft-apps` (after `7zip`) instead of `office` and `office-finish`; BUSINESS and HOME plan what they did before.
- **Choices** also hold `Profile` (an ASCII profile id, `''` = none), `Tweaks` (ASCII tweak ids) and `RestorePoint` (a bool); a state from before the toolbox has none of them, which every reader treats as no profile, no tweaks, no restore point. **Every reader of the tweaks goes through `Get-EffectiveTweaks`** (the plan, the step, the report): it keeps the catalog entries named in `Choices.Tweaks` that pass `Test-TweakAllowed` (`desktopOnly` needs Type DESKTOP, `office365Only` needs Office BUSINESS or HOME, `minBuild` hides a tweak below that Windows build). The window and the console hold the profile's *selection*; **`ConvertTo-ValidChoices` runs at the `Get-SetupChoices` seam** (on the console path too), checks every key against the whitelists and stores the *effective* list in state. **`New-DefaultChoices` returns the default profile's choices** (`defaults.profile`, which wins over `defaults.office/remote/sevenZip`), so the console fallback keeps the tweaks that are on by default. A profile only fills in the options: the Type is detected, never part of a profile.
- **Registry (tweaks):** tweaks write through `Set-RegistryDword` / `Set-RegistryString` only (REG_DWORD and REG_SZ; hives HKCU, HKLM and `Registry::HKEY_USERS\.DEFAULT\`), and **never a path with a `Policies` segment** (a policy makes Settings say "managed by your organization"); `Get-TweakCatalog` also drops an entry whose path holds `/`, `*?[]` or a `.`/`..` segment. For each value the original is read first (**an original that cannot be read is never written over**), the value is written unless it already is the target, and it is read back. The originals go to `setup.log` (`Tweak value` lines), never into step Data. A refused or differing value is a yellow Note, never red. An empty value name is the key's default value (`Set-RegistryString` maps it to the provider name `'(default)'`). **`Test-AdminProtection`** (`src/Detect/Detection.ps1`; `On`, `Off` or `Unknown`) compares the process user with `Win32_ComputerSystem.UserName`: On blocks Start in the window and makes the step skip its HKCU values with a Note; Unknown counts as the same user.
- **Restore point:** `Invoke-SetupRestorePoint` runs in `Complete-SetupFinalization`, after the setup files are removed and before `EndedAt` (the snapshot is the finished PC), once per run (`State.RestorePointTried` is saved before the attempt). **The main process owns `SystemRestorePointCreationFrequency`**: it records the original (in `setup.log` and `State.RestorePointOriginalFrequency`; a read that fails means no attempt), sets it to 0, runs one bounded child (`timeoutsMinutes.restorePoint`) and puts the original back in a `finally` (a repeated finalize puts it back without a child). Known gap: a power cut or a closed console during those minutes leaves 0 (`docs/testing.md` 1.19).
- `Choices.Remote` is `ANYDESK` (the default) | `SCREENCONNECT` | `BOTH`; **R** cycles them in that order. Every reader goes through `Get-RemoteChoice` (a missing or invalid value means ANYDESK), never through the plan list. `anydesk` runs with ANYDESK or BOTH, `screenconnect` with SCREENCONNECT or BOTH.
- `Choices.WindowsUpdate` is `FULL` (the default) | `DRIVERS`. Every reader goes through `Get-WindowsUpdateChoice` (missing or invalid means FULL). A profile may set `windowsUpdate`; one that does not leaves the choice alone, and `Test-ProfileChanged` ignores it then. The console fallback has no key for it.
- The final screen's **U** (DRIVERS only) opens `ms-settings:windowsupdate-action` through `-Launch`; its outcome replaces the blank spacer, so the screen stays at 29 lines. In DRIVERS the key line drops the report path (`[R] report   [U] Windows Update   [ENTER] finish`); FULL keeps today's line and ignores U.
- `craft-apps` (`src/Steps/CraftApps.ps1`): each `apps.craft.items` MSI from GitHub `releases/latest` runs only after its `SHA256SUMS.txt` line and an **exact** signer CN (`Test-FileSignature -ExactCN`; a company name, never a thumbprint: the certificates live 3 days). It deletes only an MSI that failed a check (V2-R13). Shortcuts are never overwritten, deleted, guessed or moved between desktops (C-R3, C-R4). A failed app is red; the launcher or a shortcut alone is yellow. `displayName`/`startMenuName` are guesses until `docs/testing.md` 1.17; details in README "Changing apps and lists".
- `screenconnect` (`src/Steps/ScreenConnect.ps1`): Ben's installer, fetched from **this release's own** URL (`v{version}`, never `latest`), runs only after its SHA-256 equals the pin in the signed `config.json` (the real proof it is Ben's file) **and** `Test-FileSignature` passes on the quoted signer `"ConnectWise, LLC"` (a substring match: **never `-ExactCN`**, it refuses a quoted subject). It deletes only an installer that failed a check (V2-R13). The exit code decides nothing: the service (read by its exact name) does. It is the one unattended remote tool and enrols the PC in Ben's list on purpose (screenconnect spec 4.6); publishing and renewal: README "A new ScreenConnect installer".
- Steps are listed in `src/Engine/Catalog.ps1`; a new step needs a catalog entry, its `Invoke-Step*` function, a `$BundleOrder` entry in `tools/Build-Bundle.ps1` (when it is a new file) and tests.
- **State** (`state.json`) shape: `New-RunState` in `src/State/State.ps1` and "Shared shapes" in the plan. Keep step `Data` shallow (`ConvertTo-Json -Depth 12` truncates silently); the key `Interruptions` is reserved by the runner.
- Context: `@{ Config; State; Root; LogDir; DownloadDir; ScriptPath; StatePath }`.
- `Get-StepPlan` returns plain ids (no comma-wrapping). `$PSScriptRoot` is empty in `param()` defaults of a `[CmdletBinding()]` script on 5.1: resolve it in the body.

## The toolbox window (step 1)
- **Four files under `src\Toolbox\` for the setup page** (the plan said three; the XAML moved out in TB-R6; the repair page adds two, below): `Strings.ps1` (the string table, en and he), `Xaml.ps1` (the XAML here-string, ASCII, every colour and size a resource), `SetupPlanner.ps1` (pure: profiles, `ConvertTo-ValidChoices`, `Test-ProfileChanged`, the window model `New-ToolboxModel` / `Update-ToolboxModel`, `Get-ToolboxPlanLines`) and `Toolbox.ps1` (the view, the handlers, `Show-ToolboxWindow` and the seam `Test-ToolboxHost` / `Get-SetupChoices`). A new file needs its `$BundleOrder` entry like any other.
- **The view renders a pure model.** Texts are `Tag="t:<key>"` TextBlocks that `Set-ToolboxLanguage` fills from the string table; clickable elements carry `Tag="a:<Action>:<Value>"`. The "What will happen" column is `Get-StepPlan` on the validated Choices, with the language's `step.<id>` names (Hebrew only in the window; the console, `setup.log` and the report keep the catalog's English titles).
- **Every handler is one line through `Invoke-ToolboxAction`, which never throws; the window's state lives in `$window.Tag`.** No closures, no `GetNewClosure()`, no outer variables (the exception: `$script:ToolboxOpenWindow`, which the dispatcher backstop `Invoke-ToolboxUnhandled` reads; the repair page adds two, below). No key handler or key binding: Start is not the default button and not focusable, and Esc is unbound. No `Write-Host`, no `Start-Sleep`. Every .NET call's output goes to `$null`, so each function returns exactly one value. `RenderOptions.ProcessRenderMode` is `SoftwareOnly` (the PC may have no GPU driver yet).
- **`Get-SetupChoices`** (`Main.ps1` calls it where it called `Show-StartScreen`: same parameters, same return, Choices or `$null`) has three window outcomes: **Start** (the validated Choices), **Cancel** (`$null`, as Esc on the console) and **Failed**. **Only Failed, or a failed host check (not STA, not interactive, session 0, WPF will not load), falls back to `Show-StartScreen`**, the emergency path, always with `-NoAutoStart`: **the console fallback waits for Enter (TB-R8)**, no countdown even on a fresh PC (without the switch `Show-StartScreen` keeps its v2 countdown). A console result that is neither `$null` nor one hashtable throws. A failure is never read as Cancel. `Dispatcher.InvokeShutdown()` runs once after the window, so the main thread does not keep a hidden WPF window for the hours the run takes. The resume path never reaches the seam.
- **The second page, Repair & diagnostics** (repair spec 4): two more files, `RepairPlanner.ps1` (pure: the page model `New-RepairModel` / `Update-RepairModel`, the strip, the gates `Get-RepairGate`, the confirmations and YES, the run model) and `RepairPage.ps1` (the view, the runs `Start-ToolboxRun`, Stop, the stick check, Open folder). **One 500 ms run timer** (`Update-ToolboxRuns`) reads each busy slot's `progress.json` / `result.json` and re-renders the repair page only, never the whole window; a slot's child past its budget + 3 minutes on its own Stopwatch is killed (`Stop-ToolboxChild`). The window never runs a setup step, never calls a hang-prone cmdlet and never sleeps: the strip is read by the `safety` child.
- **Two more script-scope exceptions** to "no outer variables", neither read by a handler: `$script:ToolboxChildren` (every process the window started, so `Get-SetupChoices`' `finally` can kill them after the window is gone) and `$script:ToolboxRestartRequested` (Restart PC).
- **The close guard** (spec 4.4): while an action runs, X, Alt+F4 and Cancel are refused ("press Stop, then close"), the nav and Start are locked. A **Failed** outcome kills every child's process tree before anything else happens (the console fallback, a cleanup). **A fourth outcome, Restart** (Restart PC): `Get-SetupChoices` returns `$null`, `Main.ps1` runs its Cancel path, then `Invoke-StatelessRestart` (`Restart-Computer -Force`, else `shutdown.exe /r /t 5 /f`). **Open folder** opens only a folder under the stick's root, never `%SystemDrive%\BenTech` in any spelling (ruling RD-R19: Explorer's "Continue" would add the user to the admin-only folder's ACL).
- **Preview:** `tools\Preview-Toolbox.ps1` renders thirteen PNGs offscreen into `dist\toolbox-preview` (nothing is shown): six of the setup page (the last two are the UPDATES row on Drivers only, in English and Hebrew), seven of the repair page. Run it after any look change; Ben approved the look on these pictures (Q29; the UPDATES row Q41, and the small scroll it adds to the default view Q42; Q35 for the repair page).

## Repair & diagnostics (toolbox step 2)
- **The child entry** (repair spec 7, 10): `setup.ps1 -ToolAction <id> -ToolArgs <path of args.json>`. `src\Entry\Param.ps1` gained exactly these two parameters; **the launcher did not change**. `Start-BenTechSetup` hands the child to `Invoke-SetupToolProcess`, like `-WuRound`: no lock, no transcript, no screen, no activity feed. The child never draws and never prompts: every question was answered in the window.
- **The catalogs** live in `src\Repair\ToolEngine.ps1`: `$script:ToolActionCatalog` (per action: `Kind` info/readonly/repair/destructive, `Confirm` none/confirm/yes, `NeedsStick`, `LogLocal`, `Steps`) and `$script:ToolSteps` (per step: `Function` = `Invoke-ToolStep<Id with its first letter upper-cased>`, `Servicing`, optional `AlwaysRun`). A new action or step needs its rows, its function, `tool.step.<id>` and every `finding.<Code>` it adds in `Strings.ps1` (en and he), and tests.
- **The step contract:** `Invoke-ToolStep<Name> -Run <hashtable>` returns exactly one of `done`, `warn`, `failed`, `skipped` (or `timedout`); findings go through `Add-ToolFinding` (English text from the string table, ASCII args); shared data in `$Run.Data` (keys in `$script:ToolResultHiddenData` stay out of `result.json`, which the window reads only under 1 MB). A step that throws is `failed` (`stepFailed`) and the next one still runs (DISM failing must not stop SFC). A step that sets `$Run.Data.Abort` ends its action after it (no verified network backup or ghost CSV, no reset or removal). `AlwaysRun` steps run even after a Stop, an Abort or the deadline (`wuServicesStart`, `reportWrite`). `Servicing` steps are re-checked for a pending servicing restart first.
- **Stop works only between steps** (spec 4.3): the window writes `stop.flag`, the runner reads it between steps. DISM, SFC and the disk scan end only by their own timeout or the action's deadline. **Deadlines run on a monotonic clock** (RD-R8): the child gets `BudgetSeconds` in `args.json` and measures it on one Stopwatch; a step's timeout is capped by the time left; nothing compares the wall clock (`timeSync` moves it).
- **Never parse tool text.** Decisions come from exit codes (DISM's HRESULT), enums, CIM, the registry, event provider + ID + `Properties`, SIDs and CBS.log (always English). The one read of a tool's output is DISM's percent from its redirected output file (`Invoke-ToolNative -OutputName`: `cmd.exe /d /s /c ""<tool>" <args> > "<file>" 2>&1"`), display only; no `-CaptureOutput` anywhere in `src\Repair` (`tests\RepairStatic.Tests.ps1` pins it and the file reads allowed).
- **The files of a run** live in `C:\BenTech\Setup\Tool\<RunId>\`, admin-only, never on the stick: `args.json` (the window), `progress.json` and `result.json` (the child), `stop.flag`. Every JSON file is written to `<file>.tmp` and swapped in. `Read-ToolJsonFile` reads them with a 1 MB cap; a report's `_data.json` is read with `$script:ToolReportDataMaxBytes` (16 MB, RD-R23).
- **The session folder**, one per visit: `<stick>\BenTech-Reports\<PC>_<serial>_<yyyy-MM-dd_HHmm>\` (`<serial>` = `Get-MachineIdentity`'s FolderPart: the serial, or `UUID-<last 12 hex>` for a placeholder; the stamp is when the page opened). The child creates it (`New-ToolSessionDir`) and **never writes through a link** (V2-R13: it falls back to `<Root>\Logs\Repair\<leaf>` with `sessionLink` or `sessionCreateFailed`). The info children (`safety`, `netInfo`, `ghostList`) log locally (`LogLocal`). The reports, Compare, Network reset and Ghost devices need the stick.
- **Reports and privacy** (spec 6.8, Q33): `REPORT_<PC>_<stamp>.txt` (the AI-ready core, under `repair.reportMaxKB`), **`REPORT_SAFE_<stamp>.txt`** (`src\Repair\ToolPrivacy.ps1`: one masker per file over the report's known personal values and the patterns; it reads parsed values and text, never raw JSON; it fails closed, so no SAFE file ever holds unmasked text; no PC name in a SAFE file name, RD-R4), `_data.json` and `raw_<stamp>\`. **Compare with last visit** (`src\Repair\ToolCompare.ps1`): the identity key must be equal (an empty key never matches: white boxes are never merged), only this PC's visit folders are read, today's visit never counts, and a data file of this PC that cannot be read is named in the report and the window, never skipped in silence (RD-R23). The `compare` action writes its own `COMPARE_` files and `_data.json`, so it is a visit too.
- **Tests:** every repair test file mocks `Invoke-External`, `Invoke-PowerShellChild`, `Invoke-ToolJsonChild`, `Start-BackgroundExternal`, `Stop-ProcessTree`, CIM, the registry, `Get-WinEvent` and the Storage/DISM/Net cmdlets it reaches, plus safety-net mocks that throw (`Start-Process`, `Restart-Computer`, the service, network, volume and registry-writing cmdlets). `tests\fixtures\ReportFakePc.ps1` is the fake Hebrew Dell the report, SAFE-copy and Compare tests run the real collectors on. No test reads this PC's personal data.

## Sign and publish flow (R29)
- Private key: `%USERPROFILE%\.bentech-winsetup\signing-key.dpapi` (DPAPI, never in the repo). Public key: `keys/public-key.xml`, built into every launcher. **The private-key backup MUST be in Ben's password manager before the first publish; verify it** (README "Signing key" has the procedure). The private key must never be written to a file outside the DPAPI store (except a short-lived `-BackupPath` file such as `bentech-signing-key-BACKUP.xml`, in a non-synced folder, deleted permanently as soon as the password manager holds the key), and never put in a synced folder, a repo, or a chat. Moving it into the password manager through the clipboard is the intended route (README procedure, with Windows clipboard history and sync OFF).
- `tools/Publish.ps1 -Version yyyy.MM.dd.N [-Notes ..] [-DryRun]`: needs a clean tree and a pushed HEAD (warnings only under `-DryRun`), runs the tests, builds the bundle, signs, verifies, builds the launcher, then `gh release create v<Version> --target <HEAD>` with exactly **five** files: the four signed ones (`setup.ps1`, `config.json` and their `.sig`) plus `ScreenConnect.ClientSetup.exe` (no `.sig`: `config.json` pins its SHA-256). Publish reads that installer from `%USERPROFILE%\.bentech-winsetup\` and checks it before building (it exists, its SHA-256 matches, a `Valid` ConnectWise signature; `-DryRun` only warns). The launcher still fetches only the four signed files.
- **R29: the launcher is never uploaded.** It is the trust anchor (it holds the public key). Publish prints its SHA-256 and records it in `keys/launcher.sha256`; Ben keeps `dist\BenTechSetup.cmd` on his USB stick and re-copies it only when that hash changes (new key or changed template). Commit the updated hash file.
- The v2, Craft, ScreenConnect, toolbox and Repair & diagnostics work left the launcher untouched: `launcher\BenTechSetup.template.cmd` and `keys\public-key.xml` are unchanged and `keys\launcher.sha256` stays `702c323a...` (pinned by `tests\Launcher.Tests.ps1`). A publish dry run must not print `WARNING: the launcher changed`; if it does, every USB stick needs the new launcher.
- R30: the launcher calls `powershell.exe` and `fltmc.exe` by full path. Its own path reaches PowerShell only through `set "BT_SELF=%~f0"` / `$env:BT_SELF`, never inside a quoted PowerShell string (an apostrophe in the path would break it).
- Launcher exit codes: 0 ok, 1 unexpected error, 2 already running, 3 signature check failed, 4 cannot download, 5 cannot secure `C:\BenTech`.
- Rollback: `gh release edit v<old> --latest`. A lost key means a new key and a new launcher on every stick.

- **Never run setup steps, `setup.ps1`, the launcher, `msiexec`, a downloaded installer or any repair or diagnostic tool (`dism`, `sfc`, `chkdsk`, `reagentc`, `netsh`, `pnputil`, `fsutil`, `chkntfs`, `w32tm`, `sc`, `msinfo32`) on this machine.** In particular never run `ScreenConnect.ClientSetup.exe` (any copy, in `Downloads\` or `%USERPROFILE%\.bentech-winsetup\`): it would enrol this PC in Ben's ScreenConnect list; and no test may read Ben's real installer.
